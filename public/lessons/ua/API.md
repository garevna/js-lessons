@@@@

## ![ico-25 icon] CRUD

[** ♫**](sounds/ua/api-crud.mp3)

Як правило, будь-який додаток взаємодіє зі своїм бекенд-апі, розташованим на сервері.
Бекенд-апі забезпечує додатку доступ до даних, які зберігаються на сервері, за допомогою методів **CRUD**.

^^^[CRUD]

**CRUD** (_create_, _read_, _update_, _delete_) — це чотири основних типи запитів до сервера.

Для ідентифікації типу запиту використовується **метод доступу**, або **дієслово**, яке ідентифікує операцію з ресурсом.

| **GET** | **POST** | **PUT** | **PATCH** | **DELETE** | **HEAD** |

| ~read~   | **GET**   | отримати дані       |
| ~create~  | **POST**   | створення нового ресурсу (нового запису)  |
| ~update~  | **PUT**   | повне оновлення наявного ресурсу (запису)    |
| ~update~  | **PATCH**  | часткове оновлення наявного ресурсу (запису)        |
| ~delete~  | **DELETE** | видалення ресурсу      |
| ~read~   | **HEAD**   | отримання інформації про ресурс              |

^^При цьому вам абсолютно неважливо, як саме ці дані зберігаються на сервері: у вигляді окремих файлів чи у вигляді записів у базі даних.^^

^^^

## ![ico-25 icon] Request & Response

[** ♫**](sounds/ua/api-request-response.mp3)

Будь-який API працює за принципом «запит» — «відповідь».
Ваш застосунок надсилає запит, і якщо запит валідний, то API надсилає застосунку відповідь.

Форма запиту залежить від API.
Це може бути метод, наприклад, **~setTimeout~** або **~fetch~**.
Це може бути об'єкт, властивості та методи якого забезпечують вам доступ до можливостей браузерного API. Всі об'єкти **~BOM~** і **~DOM~** є елементами браузерного API.
Це може бути конструктор, який ви використовуєте для створення об'єктів, які надають вам доступ до можливостей браузерного API. Наприклад, конструктор **~XMLHttpRequest~** або конструктор **~FileReader~**.

### ![ico-25 icon] Resource

[** ♫**](sounds/ua/api-resource.mp3)

Головне при взаємодії з серверним API - визначити зміст поняття "ресурс" і присвоїти кожному ресурсу унікальний ідентифікатор.

^^Наприклад, в якості ресурсу може виступати інформація про юзера. Тоді, знаючи унікальний ідентифікатор ресурсу, ви можете надіслати запит серверному АПІ на отримання даних юзера за його ідентифікатором (**GET**), можете надіслати запит на зміну даних юзера (**PUT** або **PATCH**) або ж відправити запит на створення нового юзера (**POST**).^^

Таким чином, при взаємодії з віддаленим API під терміном "ресурс" ми маємо на увазі **деякий фрагмент інформації, що має унікальний ідентифікатор.**

^^Різниця між **URL** (Uniform Resource Locator) і **URI** (Uniform Resource Identifier) полягає саме в тому, що **URL** вказує точне місце розташування ресурсу на сервері, а **URI** вказує тільки ідентифікатор ресурсу. **URI** забезпечує більшу гнучкість серверного API з точки зору розміщення даних та форми їх зберігання.^^

Ресурсом може бути файл, що зберігається на сервері, або окремий запис у базі даних.

Наприклад, на сервері може зберігатися файл зображення, але те ж саме зображення може зберігатися в базі даних у вигляді текстового рядка у форматі [**Base64**](https://www.base64encode.org/).

## ![ico-25 icon] API endpoints

[** ♫**](sounds/ua/api-endpoints.mp3)

Кожен API має документацію та специфікації, які визначають спосіб передачі інформації.

^^^[![](icons/swagger-logo.svg)]
![](illustrations/api-endpoints-01.png)
^^^

API-інтерфейси можуть використовувати HTTP-запити для отримання інформації від веб-додатка або веб-сервера.

У випадку REST API запит здійснюється через інтернет і приймає форму певної веб-адреси, яка називається **~endpoint~** (точка доступу до віддаленого API).

^^^[![](icons/api-endpoints.svg)]
^^Поняття "endpoint" використовується не лише в контексті REST API, але й у більш широкому сенсі в сфері інформаційних технологій та мережевих взаємодій.^^

^^• У мережевих протоколах термін «endpoint» може позначати будь-яку кінцеву точку зв’язку в мережі, будь то IP-адреса та порт у TCP/IP, або кінцеву точку в маршрутизації повідомлень.^^
^^• У SOAP (Simple Object Access Protocol) API endpoint також позначає URL-адресу, на яку надсилаються SOAP-повідомлення. Це схоже на REST API, але використовується в інших протоколах та форматах даних.^^
^^• У GraphQL API endpoint представляє собою одну кінцеву точку, через яку клієнт може запитувати конкретні дані, використовуючи складні запити.^^
^^• У мікросервісах endpoint може позначати будь-яку точку входу для взаємодії з окремим мікросервісом. Кожен мікросервіс може мати свої власні endpoints для різних функціональностей.^^
^^• У більш широкому сенсі, endpoint може позначати будь-яку точку, через яку здійснюється доступ до ресурсу або послуги, будь то всередині системи або між різними системами.^^
^^^

**~endpoint~** - це URI-подібний рядок, який надає вам API для віддаленого доступу до ресурсів.

Давайте розберемося, що ж включає цей рядок.
Почнемо з того, що сам **API** має **URL**, наприклад: https://api.example.com. І цей **URL** обов'язково буде присутній у кожному **~endpoint~**.
Однак для доступу до ресурсу потрібно вказати, який саме ресурс вас цікавить, і що ви хочете зробити з цим ресурсом (отримати ресурс, створити новий, видалити або оновити наявний).
**~endpoint~** містить всю цю інформацію.

Як ми вже говорили раніше, кожен ресурс має унікальний ідентифікатор і з кожним ресурсом може бути виконаний ряд різних операцій (читання, створення, видалення, оновлення/зміна).

Таким чином, **~endpoint~** не є ні **URL** (оскільки не містить інформації про розташування ресурсу), ні **URI** (оскільки включає в себе не тільки ідентифікатор ресурсу, але й інформацію про операцію з ресурсом).

![ico-25 warn] Якщо якась операція з ресурсом допустима, то для неї є **~endpoint~**.
![ico-25 warn] Якщо такого **~endpoint~** немає, то дана операція з ресурсом неможлива.

^^^[![](icons/swagger-logo.svg)]
![](illustrations/api-endpoints-02.png)
^^^

^^^[![](icons/swagger-logo.svg)]
![](illustrations/api-endpoints-04.png)
^^^

^^^[![](icons/coffee.svg)]
^^Розглянемо приклад з API ~https://api.example.com~.^^
^^Припустимо, на сервері зберігається база даних користувачів.^^
^^API дозволяє отримати список усіх користувачів і надає вам для цього **~endpoint~**:^^

••https://api.example.com/users/all••

^^Для отримання інформації конкретного користувача з унікальним ідентифікатором **iserId** ендпоінт буде вже іншим:^^

••https://api.example.com/users/${iserId}••


^^Для створення нового користувача (**POST**):^^

••https://api.example.com/user/create••

^^Для повної заміни всіх даних користувача (**PUT**):^^

••https://api.example.com/user/change/${iserId}••

^^Для часткової модифікації даних користувача (**PATCH**):^^
••https://api.example.com/user/update/${iserId}••

^^І для видалення користувача (**DELETE**):^^

••https://api.example.com/user/remove/${iserId}••

^^Серверний API парсить адресу запиту, і якщо цей рядок відповідає одному з допустимих варіантів, і якщо у вас є права на виконання таких операцій, то ваш запит виконується.^^

^^^

Ендпоінт у REST API - це точка, до якої звертається клієнт, щоб взаємодіяти з сервером.
Він являє собою не просто URL-адресу, а сукупність адреси API і маршруту, який включає ідентифікатор ресурсу та інформацію про те, яку дію треба виконати. Це як веб-адреса, але з додатковими частинами, які вказують, що саме потрібно зробити з даними.

## ![ico-25 icon] web service

**Терміни:**

| ^^![ico-20 pin] **SOA** (**_Service Oriented Architecture_**) — сервісно-орієнтована архітектура веб-додатків (набір архітектурних принципів).^^           |
| ^^![ico-20 pin] **RPC** (**_Remote Procedure Call_**) — віддалений виклик процедури.^^ |
| ^^![ico-20 pin] **Сервіс** (service) — набір операцій, які приймають запит (_Request_) і видають відповідь (_Response_).^^ |
| ^^![ico-20 pin] **Веб-сервіс** — ідентифікована веб-адресою програмна система зі стандартизованими інтерфейсами.^^       |

Веб-сервіси можуть взаємодіяти один з одним і з іншими програмами, використовуючи сповіщення, засновані на певних протоколах.

Найпоширенішим розповсюдженням відзначилися наступні протоколи реалізації **_веб-сервісів_**:

![ico-20 green-ok] **SOAP**    (_Simple Object Access Protocol_)
![ico-20 green-ok] **REST**    (_Representational State Transfer_)
![ico-20 green-ok] **XML-RPC** (_XML Remote Procedure Call_)

### ![ico-20 icon] REST API

Основний принцип **REST** полягає в обмеженні набору операцій — використовуються лише операції **CRUD** (~Create~ ~Read~ ~Update~ ~Delete~).

Архітектурний стиль **REST** у більшості випадків передбачає використання протоколу **HTTP**.

Тому команди **CRUD** перетворені на  HTTP-методи  **POST** — **GET** — **PUT** — **DELETE**.

^^^[![](icons/postman.svg)]
![](illustrations/api-rest-postman.png)

### ![ico-20 icon] SOAP vs REST

APIs зазвичай класифікуються як **SOAP** або **REST**, і обидва використовуються для доступу до веб-сервісів.

![ico-20 green-ok] **SOAP**: для обміну повідомленнями використовується формат XML
![ico-20 green-ok] **REST**:  для отримання або надсилання інформації використовуються URL-адреси

**REST** використовує чотири різні HTTP 1.1 дієвідміни (~GET~, ~POST~, ~PUT~ і ~DELETE~)

На відміну від ~SOAP~, ~REST~ не обов'язково повинен використовувати ~XML~ для надання відповіді

Існують веб-сервіси на основі REST, які виводять дані у наступному форматі:

| ^^• Command Separated Value (CSV)^^ |
| ^^• JavaScript Object Notation (JSON)^^ |
| ^^• Really Simple Syndication (RSS)^^ |

^^Можна отримати результат у форматі, який простіше парсити на мові вашого додатку^^
